# Hedera DID Anchor Spike

**Status**: Research spike — not production code  
**Purpose**: Prove that `did:hedera` creation and resolution works using the Hiero DID SDK  
**Date**: 2026-05-26

---

## What This Spike Proves

This spike replaces the prototype's `did:key` placeholder with a real `did:hedera` testnet anchor.

It proves:

1. Hedera operator credentials can submit DID operations to the Hedera Consensus Service (HCS)
2. A `did:hedera` can be created — the SDK generates an Ed25519 keypair, creates an HCS topic, and publishes the DID owner message
3. DID state becomes visible through the Hedera mirror node after the HCS transaction is confirmed
4. The DID can be resolved back into a full W3C DID Document via the Hiero resolver
5. This can later replace `createUserDid()` in `mock-heka-credo` to produce `did:hedera` subjects instead of `did:key`

---

## How This Maps to the Prototype

### Current code (MVP)

```typescript
// mock-heka-credo/src/services/credentialService.ts
createUserDid()   // -> did:key (local, no ledger)
```

`did:key` is created locally with no Hedera interaction. It is self-contained and works offline, but it is not publicly resolvable or anchored on a decentralized ledger.

### Future path (this spike's target)

```typescript
createUserDid()
  // -> create did:hedera via Hiero DID SDK registrar
  // -> submit HCS topic + owner message via RecordingPublisher
  // -> wait for mirror node visibility
  // -> return did:hedera string
  // -> issue GithubContributorCredential with subject.id = did:hedera
```

The `credentialSubject.id` in the Verifiable Credential would change from:

```json
{ "id": "did:key:z6Mk[user]" }
```

to:

```json
{ "id": "did:hedera:testnet:z6Mk[user]_0.0.[topicId]" }
```

This makes the DID publicly resolvable on Hedera testnet by anyone — without trusting a centralised server.

### RFC sentence

> The current MVP uses `did:key` to prove the credential flow without ledger dependency. The Hedera anchoring spike proves the next migration step: replacing local `did:key` creation with testnet-backed `did:hedera` creation and resolution using the Hiero DID SDK.

## Architecture

```
npm run create
    │
    ├── 1. Load .env (HEDERA_OPERATOR_ID, HEDERA_OPERATOR_KEY)
    ├── 2. Build Hedera Client (testnet)
    ├── 3. Attach RecordingPublisher (captures transaction IDs)
    │
    ├── 4. createDID() — Hiero DID SDK registrar
    │       ├── Generates fresh Ed25519 keypair for the DID owner
    │       ├── Creates HCS topic                   → transaction 1
    │       └── Publishes DID owner message to HCS  → transaction 2
    │
    ├── 5. Wait for mirror node visibility (up to 180s)
    │
    ├── 6. resolveDID() — Hiero DID SDK resolver
    │       └── Reads HCS messages from mirror node
    │       └── Builds W3C DID Document
    │
    ├── 7. Write evidence/hedera-did-anchor.json    (public, gitignored by default)
    └── 8. Write .local/private/did-owner-private-key.txt  (secret, gitignored)
```

## Setup

```bash
cd spikes/hedera-did-anchor
npm install
cp .env.example .env
```

Edit `.env`:

```env
HEDERA_NETWORK=testnet
HEDERA_OPERATOR_ID=0.0.xxxxxx
HEDERA_OPERATOR_KEY=302e...
DID_VISIBILITY_TIMEOUT_MS=180000
```

> **Important**: `HEDERA_OPERATOR_ID` / `HEDERA_OPERATOR_KEY` are your Hedera account credentials that **pay for gas fees**.  
> The DID owner private key is a separate Ed25519 key generated by the SDK — it is the key that **controls the DID**.  
> These are different keys with different purposes.

## Troubleshooting

| Error | Cause | Fix |
|-------|-------|-----|
| `INSUFFICIENT_PAYER_BALANCE` | Testnet account has no HBAR | Fund account at portal.hedera.com |
| `INVALID_SIGNATURE` | Wrong operator key for account | Double-check `HEDERA_OPERATOR_KEY` matches `HEDERA_OPERATOR_ID` |
| Visibility timeout | DID transaction succeeded but mirror node is slow | Increase `DID_VISIBILITY_TIMEOUT_MS` to `300000` |
| Resolver returns `not found` | DID visible in chain but mirror not indexed yet | Wait 30-60 seconds and run `npm run resolve` manually |
| `npm install` fails | Package registry issues | Retry, or use `npm install --legacy-peer-deps` |
